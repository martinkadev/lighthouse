# Experimental EIP-8321 validator integration

This branch ports EIP-8321 onto heze-devnet-2 as a separate fork after Heze.
Configure `EIP8321_FORK_EPOCH` and `EIP8321_FORK_VERSION` in the network configuration. It is experimental,
not an activation recommendation for a public network.

## Specification compatibility

The local `specs/_features/eip8321/{beacon-chain,validator,p2p-interface,fork}.md`
and matching generated vectors are authoritative for this branch. Do not copy
constants or SSZ layouts from the online proposal into this implementation.

| Item | Local implementation/reference | Published proposal difference |
| --- | --- | --- |
| Registration domain | `0x11000000`, from `ChainSpec` | Online EIP currently lists `0x0F000000` |
| Activation delay | `EthSpec::commitment_registration_delay()` | Do not hardcode a network-independent value in the VC |
| Operations per block | `EthSpec` list limit | Preserve minimal/mainnet preset selection |
| State and block layout | Separate EIP-8321 SSZ containers | Proposal sketches are not a replacement for the local containers |
| Chain hash | BLAKE3, default 32-byte output, `HASH_CHAIN_RANDAO` prefix | Same construction |
| Registration signing | Genesis fork version and genesis validators root | Fork-independent registration domain |

## Enabling the validator client

On a matching experimental network, pass:

```sh
lighthouse vc --randao-hash-chain-dir /secure/validator-randao-chains [other VC options]
```

This is an **opt-in to irreversible registration**. At a managed validator's
proposal duty, the VC queries that particular beacon node's proposal state. If
the validator has no active or pending commitment, it durably creates an
independent random chain secret, signs the tip, and submits the registration.
The current proposal still uses BLS. Registration retries reuse the stored tip.
Once the selected proposal state activates the commitment, the VC sends its
preimage and the BLS point at infinity. Failed registration submission is retried
at subsequent proposal duties and does not block the legacy proposal.

No changes occur when the flag is absent. If a previously registered validator
is run without its custody directory, the BN refuses to produce a block with a
missing reveal; it does not silently fall back to BLS.

## Custody, backup and restart

The directory contains `<genesis_validators_root>/<validator_pubkey>.json`.
Files contain a **plaintext secret seed**, the chain length, verified tip,
validator index, public key, network root and format version. Protect and back
up this directory independently of the signing keystores. On Unix, files are
created with mode `0600`, network subdirectories with `0700`, and files with
group/other permissions are refused. Use an encrypted volume if at-rest
encryption is required. Backup processes must include newly created files.

Each chain has 65,536 links, generated from random bytes rather than from the
validator signing key. Atomic no-clobber installation, file sync, and directory
sync complete before registration signing. Existing files are never replaced.
Every load verifies the identity, entire chain and tip. Unknown commitments,
corruption, missing active/pending custody, zero links and exhaustion fail closed.

There is no persistent reveal cursor. The canonical commitment selects the
preimage. Restarting, retrying a request, switching beacon nodes, or returning to
an earlier branch therefore does not consume an extra link. Keep normal
slashing-protection files when moving or restarting the VC; hash-chain custody
does not replace slashing protection. A reorg to an unactivated registration
uses BLS again. A reorg to an older active commitment reuses that branch's
preimage, as required by the specification.

Registration cannot be changed in place. Losing or exhausting the chain stops
proposals for that validator index. Exiting and depositing under the same key
does not reset it. A replacement requires a new validator key and index.

## Experimental HTTP extensions

These are Lighthouse extensions for this branch, not finalized beacon-API standards.

* `GET /lighthouse/randao/{slot}` returns public proposal context: selected parent,
  proposer identity, network root, active commitment and optional pending tip.
  It accepts only the current or next slot. State advancement includes epoch-boundary
  activation and uses the same parent selection as production.
* `POST /eth/v1/beacon/pool/randao_commitment_registrations` accepts one signed
  registration as JSON, verifies it, pools it and publishes the existing gossip topic.
  Identical retries succeed; conflicting registrations for an already pooled index fail.
* `POST /eth/v4/validator/blocks/{slot}` accepts optional `hash_chain_reveal=0x...`
  for both JSON and SSZ responses. The existing builder-config body stays unchanged.
  The BN checks the preimage against the state actually used for production, even
  when BLS verification is skipped. A stale context can fail safely; subsequent
  fallback requests query their own beacon node again. The VC checks the returned
  block contains exactly the requested reveals before signing.

The seed and undisclosed future preimages are never sent to the BN. As with block
production generally, use trusted beacon nodes and protect the API connection.
Avoid logging V4 query strings: a requested preimage is intended for the next
proposal, not general-purpose logging.

Local signing is covered by the lifecycle tests. The signing adapter also defines
an experimental `RANDAO_COMMITMENT_REGISTRATION` remote-signing object with genesis
fork info and signing root. External signers must explicitly support that object;
compatibility with an unmodified Web3Signer server is not implied.

## Regression tests

```sh
cargo nextest run --release -p lighthouse_validator_store -p validator_services \
  -p signing_method --features spec-minimal --no-fail-fast
cargo nextest run --release -p http_api --features spec-minimal \
  --test bn_http_api_spec_minimal_tests -E 'test(randao_lifecycle_tests)'
cargo test --release -p ef_tests --features ef_tests --test tests eip8321_
cargo test --release -p ef_tests --features ef_tests,spec-minimal --test tests eip8321_
```

The lifecycle test uses real validator keys/custody, HTTP registration and V4
production, actual activation transitions, signed block imports, reopening the
same slashing database and custody files, and a competing fork-choice branch.
The validator-service test covers proposal publication and different commitment
contexts returned by two beacon nodes. These tests use a mock execution
layer; they are not a live multi-client devnet certification.
